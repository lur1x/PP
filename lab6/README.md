## Цели и задачи

## Задание 1

### Постановка задачи
Необходимо разработать программу, которая вычисляет приближенное значение числа π, используя метод Грегори–Лейбница.

**Формула:**
```
π = 4 * (1 - 1/3 + 1/5 - 1/7 + ...)
```

При разработке программы необходимо использовать библиотеку OpenMP.

Должно быть проверено и подготовлено несколько вариантов программы:
1. С использованием `for` (синхронно)
2. С использование параллельного `for` (работает неверно)
3. Рабочее решение с использованием `parallel for` и `atomic`
4. С использованием `reduction`

### Требования
1. Программа должна быть реализована в виде консольного приложения и использовать библиотеку OpenMP, язык программирования – С++.
2. Рассказать про `for`, `reduction`, `parallel`, `atomic`.
3. Записать время выполнения вариантов программ и сравнить. Объяснить различия во времени выполнения при использовании различных вариантов (`reduction`, `atomic` и т.д. см. в задании).

## Задание 2

### Постановка задачи
Необходимо объяснить разницу между `private(x)`, `firstprivate(x)` и `lastprivate(x)` на примере ниже.

```cpp
int main()
{
    int x = 44;
    #pragma omp parallel for private(x)
    for(int i = 0; i <= 10; i++){
        x = i;
        printf("Thread number: %d x: %d\n", omp_get_thread_num(), x);
    }
    printf("x is %d\n", x);
}
```

# Выводы по 1 заданию:

### 1. **Корректность результатов**
*   **Последовательная версия, atomic и reduction** дали одинаковый и правильный результат (`3.14159`), что совпадает с константой `M_PI`. Это подтверждает математическую корректность реализации.
*   **Версия с состоянием гонки (`ParallelRace`)** выдала неверный результат (`3.14281`). Это является наглядной **демонстрацией ошибки параллелизма**, возникающей при одновременной несинхронизированной записи в общую переменную `pi` из разных потоков. **Этот вариант непригоден для практического использования.**

### 2. **Производительность (время выполнения)**
Ранжирование методов от самого быстрого к самому медленному:
1.  **`Parallel (reduction)` (0.0153 с)** – **Абсолютный лидер по скорости.** Механизм `reduction` оптимален для операций суммирования: каждый поток вычисляет свою частную сумму, которые эффективно объединяются в конце, минимизируя конфликты.
2.  **`Sequential` (0.1096 с)** – Базовый вариант.
3.  **`Parallel (with data race)` (0.0667 с)** – Хотя результат неверен, по скорости он обогнал последовательный метод. Это показывает, что сам по себе параллельный цикл работает, но отсутствие синхронизации делает вычисления бессмысленными.
4.  **`Parallel (atomic)` (0.5122 с)** – **Самый медленный вариант**, даже медленнее последовательного. Операция `#pragma omp atomic` обеспечивает корректность, но создаёт "бутылочное горло": все потоки выстраиваются в очередь для обновления одной переменной, что сводит на нет преимущества параллелизма.

### 3. **Ключевые выводы по использованию OpenMP**
*   **`reduction` – это правильный инструмент для задач типа "суммирование" или "умножение".** Он обеспечивает и корректность, и высокую производительность, скрывая от программиста сложности синхронизации.
*   **`atomic` – это "тяжелый" инструмент.** Его следует использовать осторожно, только для защиты очень коротких критических секций (например, инкремента счётчика), когда другие способы (вроде `reduction`) не применимы. Для накопления суммы в цикле он категорически не подходит.
*   **Состояние гонки (data race) – самая коварная ошибка.** Программа может работать быстро и *иногда* выдавать правильный результат (особенно на малом числе итераций), что затрудняет отладку. **Обязательно нужно проверять корректность параллельных программ.**

### 4. **Общий итог для лабораторной работы**
Лабораторная работа успешно демонстрирует эволюцию и важность корректной синхронизации в параллельном программировании:
1.  **Без синхронизации** – результат быстрый, но неверный (Race).
2.  **Примитивная синхронизация (`atomic`)** – результат верный, но производительность катастрофически падает из-за сериализации.
3.  **Оптимальная синхронизация (`reduction`)** – результат верный, а ускорение (**speedup**) по сравнению с последовательной версией составляет `0.1096 / 0.0153 ≈ 7.2 раза`. Это отличный показатель эффективности параллелизма для данной задачи.
